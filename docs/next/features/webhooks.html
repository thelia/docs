Webhooks

Added in Thelia 3.3.

A shop can notify other systems of what happens in it: an ERP that wants every new order, a CRM that wants every new customer. A webhook is an HTTPS request Thelia sends, on its own, to an address you give it, each time one of the events you chose happens. The request is signed, so the receiver knows it comes from your shop and was not altered.

Both tables (webhook_subscription, webhook_delivery) arrive empty on a shop that updates: nothing is sent until a subscription exists.

Subscribing​

A subscription is an address, the events it asks for, a signing secret, a content mode and a state.

FieldMeaning
titleA name for you, up to 255 characters.
urlWhere the requests go. https only, never a private or internal address (see Addresses).
eventsThe names of the events it asks for, at least one (see Events).
payloadModefull (default) sends the whole object, identifiers sends only its id.
statusactive (default) or inactive. A subscription can also be in error: see Delivery.

The secret is generated by the shop. It is shown once, when the subscription is created and when it is replaced, and never read back: copy it then. A lost secret is replaced, not recovered.

The subscriptions answer to their own permission, admin.configuration.webhook, granted to no profile by default: an account that could create an address could send the orders of the shop to it. The superadministrator always has it.

In the back office​

Configuration, Webhooks lists the subscriptions, creates, edits and deletes them, replaces a secret, sends a signed test request, and shows the delivery log with a replay button for a failed delivery.

With the API​

OperationEndpoint
List, createGET, POST /api/admin/webhook-subscriptions
Read, update, deleteGET, PATCH, DELETE /api/admin/webhook-subscriptions/{id}
Replace the secretPOST /api/admin/webhook-subscriptions/{id}/secret
List, read the delivery logGET /api/admin/webhook-deliveries, GET /api/admin/webhook-deliveries/{id}
curl -X POST https://shop.example.com/api/admin/webhook-subscriptions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "ERP",
    "url": "https://erp.example.com/hooks/thelia",
    "events": ["order.created", "order.paid"]
  }'

The answer carries the subscription and, this once, its secret:

{
  "id": 3,
  "title": "ERP",
  "url": "https://erp.example.com/hooks/thelia",
  "events": ["order.created", "order.paid"],
  "payloadMode": "full",
  "status": "active",
  "failureReason": null,
  "failedAt": null,
  "secret": "b1c0…64 hexadecimal characters…",
  "createdAt": "2026-10-20T11:00:00+02:00",
  "updatedAt": "2026-10-20T11:00:00+02:00"
}
  • An update only changes what it carries: PATCH {"status": "inactive"} switches the subscription off and leaves the rest alone. Writing active to a subscription in error puts it back to work and clears the failure. error cannot be written.
  • The secret is not an input. POST …/secret replaces it and answers with the new one; the old one stops signing at once.
  • The address and the event names are checked by the same rule as in the back office. A refusal answers 422 and nothing is stored.
  • The delivery log is read only. It shows the outcome of each request (subscriptionId, event, deliveryUuid, status, attempts, responseCode, durationMs, deliveredAt, replayedAt, createdAt) and filters on subscriptionId, event, status, deliveryUuid and on createdAt[after] / createdAt[before]. It does not show the body that was sent nor the answer of the receiver: the first holds personal data, the second whatever the receiver chose to echo back. Pages are 25 items long and capped at 50.

Events​

EventSent whenBody
order.createdan order is placed, or created through the admin APIthe order
order.status_changedthe status of an order changesthe order
order.paidan order comes into a paid status (paid, processing, sent)the order
customer.createda customer account is createdthe customer
product.updateda product is saved with a changethe product

There is no stock event: the core takes stock with a single atomic statement that dispatches nothing.

A module adds its own events by appending name => ['resource' => ResourceClass::class, 'groups' => [...]] to the thelia.webhook.events container parameter, and calls WebhookPublisher::publish($name, $model) from its own listener.

The request​

Every request is a POST with a JSON body and three headers:

HeaderContent
X-Thelia-Webhook-IdA unique identifier for this delivery, the same on every retry.
X-Thelia-Webhook-TimestampThe Unix time the request was signed.
X-Thelia-Webhook-Signaturev1= followed by the signature (see Verifying the signature).

The body is an envelope:

KeyContent
idThe identifier of the delivery, equal to the X-Thelia-Webhook-Id header.
typeThe event name.
created_atWhen the event was published, ISO 8601.
dataThe object.

With payloadMode set to full, data is the object as the admin API shows it (the same properties, the same nesting), with one difference: the API leaves out a property that is null, a webhook keeps it as null, so the keys a receiver reads never appear or disappear from one event to the next. Properties added by the modules installed on the shop are part of it, as they are of the admin API (the Siret and ProductLibraryImagesAddon keys below come from two modules).

With identifiers, data is only {"id": 42}, for a receiver that fetches what it needs through the API.

Personal data

A body in full mode carries customer and address data: it is personal data sent to a third party, which the register of processing of the shop has to list. The identifiers mode exists for a receiver that does not need it. The deliveries keep the body that was sent, so the same data, in clear, and maintenance:purge removes them after webhook_delivery_retention_days days (30 by default, --dry-run counts them).

Examples​

Each example is a real request, produced by the code of the shop on test data, with the secret whsec_example_secret. The body is indented to be read: the signature covers the body as it was sent, without that indentation.

Verifying the signature​

Anyone who knows the address could post to it. Check the signature before trusting a request.

The signature is v1= followed by the hexadecimal HMAC-SHA256 of <timestamp>.<raw body>, computed with the secret of the subscription. Three rules:

  1. Use the raw body, byte for byte, as received. Decoding the JSON and encoding it again changes the bytes and breaks the signature.
  2. Compare in constant time (hash_equals, crypto.timingSafeEqual), never with ==.
  3. Refuse a timestamp that is too far from now, five minutes at most, so a request that was captured cannot be replayed later. The timestamp is part of what is signed.

PHP​

function verifyTheliaWebhook(string $secret, string $rawBody, string $timestamp, string $signature, ?int $now = null, int $tolerance = 300): bool
{
    if (!ctype_digit($timestamp)) {
        return false;
    }

    if (abs(($now ?? time()) - (int) $timestamp) > $tolerance) {
        return false;
    }

    $expected = 'v1='.hash_hmac('sha256', $timestamp.'.'.$rawBody, $secret);

    return hash_equals($expected, $signature);
}

$valid = verifyTheliaWebhook(
    $secret,
    file_get_contents('php://input'),
    $_SERVER['HTTP_X_THELIA_WEBHOOK_TIMESTAMP'] ?? '',
    $_SERVER['HTTP_X_THELIA_WEBHOOK_SIGNATURE'] ?? '',
);

if (!$valid) {
    http_response_code(401);
    exit;
}

Node.js​

const crypto = require('crypto');

function verifyTheliaWebhook(secret, rawBody, timestamp, signature, now, tolerance) {
  now = now === undefined ? Math.floor(Date.now() / 1000) : now;
  tolerance = tolerance === undefined ? 300 : tolerance;

  if (!/^[0-9]+$/.test(timestamp)) {
    return false;
  }

  if (Math.abs(now - Number(timestamp)) > tolerance) {
    return false;
  }

  const expected = Buffer.from(
    'v1=' + crypto.createHmac('sha256', secret).update(timestamp + '.' + rawBody).digest('hex')
  );
  const received = Buffer.from(String(signature));

  return expected.length === received.length && crypto.timingSafeEqual(expected, received);
}

With Express, keep the raw body: app.post('/hooks/thelia', express.raw({ type: 'application/json' }), (req, res) => { … req.body.toString('utf8') … }). A body parsed by express.json() is no longer the raw body.

Delivery​

  • Answer fast, with a 2xx. Thelia waits up to 5 seconds for the receiver to start answering and 10 seconds in all, follows no redirect, and counts any other answer, or no answer, as a failure. Do the real work after answering.
  • A delivery is at least once, never exactly once. A retry carries the same X-Thelia-Webhook-Id: keep the identifiers you have handled and drop a duplicate.
  • The order of arrival is not guaranteed. A retry of an old order.status_changed can reach the receiver after a newer one. created_at of the body tells which is older.
  • Retries need a queue. The delivery is a job (DeliverWebhook, routed to async), so with a queue and a worker a slow receiver never holds back the order being saved. With a queue and a worker running, a failed attempt is retried after 1 minute, 5 minutes, 30 minutes and 2 hours (five attempts in all). Without a queue the job runs in the request that raised the event: a receiver that stays silent holds that request for up to 10 seconds per subscription, a failure is not retried and the subscription stays active. Configure a queue and run a worker before relying on webhooks in production; the subscription list of the back office warns while none is configured.
  • A request that tests your receiver is not an event. The test button of the back office sends a signed webhook.test request, logged like any delivery under that name; it is not counted in the last successful delivery of a subscription.
  • A webhook raised inside a transaction. With a queue, a message that a worker reads before the transaction of the API write commits is looked for again a few times instead of being dropped. Without a queue the request leaves before the commit: a rollback that follows leaves the receiver with an event that did not happen.
  • A subscription whose retries ran out goes to error and stops receiving. Its failureReason says which delivery failed. An administrator enables it again once the receiver is fixed; a failed delivery can be replayed from the delivery log of the back office. A replay that fails does not put the subscription back in error. A replay is one attempt: it keeps the attempts already made in attempts, and a delivery that was queued when its subscription was turned off, or went to error, is recorded as cancelled and never sent.
  • Replacing the secret does not touch the deliveries already waiting for a retry. A retry is signed with the secret in force when it is sent, so a receiver that has not yet been given the new secret refuses those retries.

Addresses​

The address is entered by an administrator, so it is checked as an attack vector. https only (the thelia.webhook.allow_insecure_urls parameter allows http, for a development shop), no credentials in the address, no localhost or internal suffix (.local, .internal…), and no private, reserved, loopback, link-local, shared, multicast or documentation address, in any spelling (127.1, decimal, hexadecimal, IPv6, NAT64, 6to4).

The check reads the spelling of the address when the subscription is saved and when a delivery is sent. It does not resolve names: the HTTP client of the webhooks (thelia.webhook.http_client) is the barrier against a name that points to a private address, and it refuses to connect to a private network whatever the name resolves to.
