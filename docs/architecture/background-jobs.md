# Background jobs

Some work does not have to happen while a customer waits for a page: handing a mail to the
mail server, writing a large export, pushing stock to a marketplace. Thelia runs that work
through [Symfony Messenger](https://symfony.com/doc/current/messenger.html). Code dispatches a
message, a handler does the work, and the configuration of the shop decides whether the
handler runs at once or later, in a worker.

This page explains the model. The configuration, the commands and a complete module example
are in the [background jobs reference](../reference/background-jobs.md); running the workers
on a server is covered in [Running the workers](../getting-started/background-workers.md).

## What the core ships

The core requires `symfony/messenger`, `symfony/doctrine-messenger`, `doctrine/dbal` and
`symfony/scheduler`. It does not require the Doctrine ORM or DoctrineBundle: DBAL is only
there to serve the queue kept in the shop database.

There is one bus, `messenger.bus.default`, and three transports:

| Transport | What it carries | Where it lives |
| --- | --- | --- |
| `async` | The jobs of the shop: mail delivery, back-office exports and imports, the messages of modules | `MESSENGER_TRANSPORT_DSN`, synchronous when empty |
| `failed` | The jobs that failed every attempt | The shop database, whatever `async` is |
| `scheduler_thelia` | The recurring tasks of the `thelia` schedule | Generated by the schedule, nothing to configure |

## Nothing waits by default

`MESSENGER_TRANSPORT_DSN` is shipped empty in `.env`. An empty value makes `async` fall back
to `sync://`: every message is handled immediately, in the request or the command that
dispatched it, exactly as if the handler had been called directly. Nothing is stored and
nothing waits for a worker, so a shop that runs no worker loses no job. A failure in the
handler surfaces in the code that dispatched the message, as any exception would.

The shop opts in to a real queue by naming one:

```bash
# .env.local
MESSENGER_TRANSPORT_DSN=doctrine://default
```

From then on, `async` messages are stored and wait for `messenger:consume`. Setting the
variable without running a worker leaves mails undelivered and exports and imports pending, so the two
go together.

| DSN | Queue |
| --- | --- |
| empty | No queue, every job runs at once |
| `doctrine://default` | Table `messenger_messages` of the shop database |
| `redis://host:6379/messages` | A Redis stream |
| `amqp://user:password@host:5672/%2f/messages` | An AMQP broker such as RabbitMQ |

## The queue in the shop database

`doctrine://default` is served by `Thelia\Messenger\Transport\ShopDatabaseTransportFactory`.
It opens a DBAL connection with the settings of the Propel connection, so the queue lives in
the same database as the shop, with no extra service. Only the connection name `default` is
accepted.

The `messenger_messages` table is created by the installer and by the 3.3.0 update script.
The transport never creates it on the fly.

The DBAL connection is a second connection to the database, independent from Propel. A
message dispatched inside a Propel transaction is written to the queue at once, and stays
there even if that transaction is rolled back. A worker can then pick up a message about a
row that was never committed. Dispatch after the commit, never inside the transaction.

## Events or messages

Thelia events and messages answer different needs.

An event, dispatched through the event dispatcher, tells every listener that something
happens, and every listener runs before `dispatch()` returns. Listeners can change the event,
stop its propagation, or make the action fail. Events stay synchronous whatever the
configuration of the queue: the event dispatcher is not a message bus. See the
[events reference](../reference/events.md).

A message asks for one piece of work to be done by its handler, now or later, without the
caller depending on the result. Use a message when:

- the work is slow or calls a remote service (a mail server, a marketplace, an ERP),
- the caller does not need its result to answer,
- the work can be retried on its own if it fails.

The two combine. A listener that reacts to an event but does not need to do the work in the
request dispatches a message, and the handler does the work:

```php
public function onStockUpdated(ProductSaleElementUpdateEvent $event): void
{
    $this->bus->dispatch(new PushStock($event->getProductSaleElementId()));
}
```

The listener stays fast, and the handler gets the retries and the failure handling described
below.

## Retries and failed jobs

When a handler throws on the `async` transport, the message is retried three times, after
30 seconds, 2 minutes and 8 minutes (a multiplier of 4, plus the random jitter Symfony adds).
After the last attempt it goes to the `failed` transport. A message is never lost and never
retried in a loop.

A handler that knows a retry cannot help, for instance because the remote service rejected
the data, throws `Symfony\Component\Messenger\Exception\UnrecoverableMessageHandlingException`
and the message goes to `failed` at once.

`failed` is `MESSENGER_FAILURE_TRANSPORT_DSN`, which defaults to
`doctrine://default?queue_name=failed`: the failed jobs are always kept in the shop database,
whatever queue `async` uses, so the back office has a single place to read them from. They
stay there until someone replays them, removes them, or the purge task deletes them.

Because a failed job can be replayed, and because a retry runs a handler that may have done
part of its work, a handler must be idempotent: run twice, its effect happens once. The
reference shows how in [Idempotence and replay](../reference/background-jobs.md#idempotence-and-replay).

## What a worker sees

A handler running in a worker has no HTTP request, no visitor, no session and no cart. It
runs in a long process that handles one message after another, so the core resets the state
of the shop before each message (`Thelia\Messenger\EventListener\WorkerStateResetListener`):

- settings are read again from the database, so a change made in the back office since the
  previous message is seen,
- the active languages, the default country, the module configuration, the rewritten URLs and
  the price currency are forgotten,
- the translator is set back to the default language.

Symfony also resets the services tagged `kernel.reset` between messages, unless the worker is
started with `--no-reset`.

A handler therefore never relies on what a request would have set. It receives ids, reads its
data again, chooses the locale explicitly, and builds absolute URLs from `DEFAULT_URI`.

## What the core sends through the queue

Three jobs of the core are routed to `async`.

### E-mails

`Symfony\Component\Mailer\Messenger\SendEmailMessage` is routed to `async`. The mail is
rendered in the request, where the language and the shop URL are known; only the delivery to
the mail server is deferred. With a queue, a slow or unreachable mail server no longer holds
up the page that sends the mail, and a mail that could not be delivered ends up in `failed`,
ready to be sent again.

The order history line `email_sent` is written when the mail server accepted the mail. A
listener on the Symfony Mailer `SentMessageEvent` reads the `X-Thelia-Order-Id` and
`X-Thelia-Message-Code` headers of the mail. With a worker, the line appears when the worker
delivered the mail, and its author is `system`.

With a queue, `MailerFactory::send*OrFail()` only throws when the mail could not be built or
queued. A delivery failure happens later, in the worker.

### Back-office exports and imports

An export started from the back office is a job.
`Thelia\Domain\DataTransfer\Job\ExportJobLauncher::launch()` records an `export_job` row and
dispatches `Thelia\Domain\DataTransfer\Job\RunExportJob`. Without a queue, the export runs in
the request and the file is served at once. With a queue, the back office shows
the job page (`/admin/export/job/{id}`): waiting, running with the number of rows written
(refreshed every 3 seconds), done with a download link, or failed with the reason.

A finished export is never run twice. A failed one is recorded on its row and goes straight to
`failed`; replaying it starts it over. `maintenance:purge` deletes the jobs older than 7 days,
and the export files are deleted after a day.

An import started from the back office is a job too.
`Thelia\Domain\DataTransfer\Job\ImportJobLauncher::launch()` checks the file extension in the
request, moves the uploaded file to `var/data-transfer/import/<Ymd>/`, records an `import_job`
row and dispatches `Thelia\Domain\DataTransfer\Job\RunImportJob`. The file is kept outside the
cache on purpose: a deployment empties the cache, and a queued import would lose its file.
Without a queue, the import runs in the request and the back office shows the outcome: the
number of rows imported and the rows refused with their reason. With a queue, the job page
(`/admin/import/job/{id}`, refreshed every 3 seconds) shows waiting, running, done with the
rows changed and the rows refused, or failed with the reason.

A finished import is never run twice. A failed one goes to `failed`, and replaying it runs it
again from the first row. Each row is written on its own, so the rows written before the
failure are written again, with the same values. The uploaded file is deleted once the import
is done, and kept while the job may be replayed. `maintenance:purge` deletes the import jobs
older than 7 days and their files.

Both jobs share the status enum `Thelia\Domain\DataTransfer\Job\JobStatus`: `queued`,
`running`, `done`, `failed`.

## Recurring tasks

The recurring tasks of the shop are declared in a Symfony Scheduler schedule named `thelia`
(`Thelia\Scheduler\TheliaSchedule`). A worker consuming `scheduler_thelia` runs them; until
one does, nothing runs, and a shop can keep its crontab instead. The schedule is stateful and
locked through `LOCK_DSN`, so two workers never run a task twice, and a worker that restarts
after a missed run catches up the last one only. The tasks and their settings are listed in
the [reference](../reference/background-jobs.md#recurring-tasks).

## Which classes a queue accepts

A queued message is data that is turned back into objects when a worker reads it, and whoever
can write to the queue would choose their classes. Thelia never uses PHP serialization for
this. Envelopes are JSON, written and read by the Symfony serializer through
`Thelia\Messenger\Serializer\AllowedClassesSerializer`, which checks the classes before
building anything:

- a message class must be under `Thelia\`, under the namespace of an active module (the
  namespace named after the module code, such as `MyModule\Message\SyncStock`),
  `Symfony\Component\Mailer\Messenger\SendEmailMessage`, or listed by its exact name in the
  container parameter `thelia.messenger.allowed_message_classes`,
- a stamp must be a Messenger stamp or come from those same namespaces, and `SerializerStamp`
  is refused, as it would let the queue change how the rest of the envelope is read.

The check runs when a message is read and also when it is dispatched. A module dispatching a
class the workers would refuse gets a `LogicException` ("is not one the shop queues") at
dispatch time, not a queue that never empties.

For a module author, this means:

- message classes live in the module namespace,
- they can be written and read as JSON by the Symfony serializer: public or promoted
  constructor properties with scalar types, such as ids and codes,
- they never carry a Propel model. The handler reads the row again from its id.

A class from outside these namespaces, such as an application class under `App\`, is
accepted only once a project adds its exact name to `thelia.messenger.allowed_message_classes`.

## Personal data

A queue holds personal data: a queued mail carries the address of its recipient and the
content of the order, and a failed job keeps everything it was dispatched with. Treat the
queue like the database:

- a Redis or AMQP broker must not be reachable from outside the hosting,
- its credentials go in `.env.local` or the secrets of the hosting, never in Git,
- the retention of failed jobs is a processing to record in the GDPR register. The
  `thelia:messenger:purge-failed` task deletes them after 30 days by default.

See [Personal data](../security/personal-data.md) and
[Running the workers](../getting-started/background-workers.md#personal-data-in-the-queue).
